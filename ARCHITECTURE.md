# `rship` Architecture

> **Public Documentation**: Browse the full interactive documentation site at [https://hua0512.github.io/rship/](https://hua0512.github.io/rship/).

---

## 1. Core Architectural Invariants

1. **Low Memory Footprint, Explicit Memory Scope & Permit-Bound Zero-Copy Buffers**
   - `BufferPool` is gated by a **4 KiB-unit byte semaphore** (`min(25% cgroup_limit, 16 MiB)` default, explicit `--max-buffer-mem` override).
   - Streaming buffers (`256 KiB` default slabs, plus optional `1 MiB` coalesced slabs) are wrapped in `PooledSlice` and yielded via **`Bytes::from_owner(PooledSlice)`**, keeping permits held until the final network/disk consumer drops the `Bytes` handle.
   - **Anti-deadlock rule**: no task may hold > 1 `PooledSlice` or call `acquire()` while holding one. In `rship-crypto`, both decryptors (`CryptoRangeReader`, `open_full_decrypt_stream`) and `StreamEncryptor` reset drained `Bytes` slices to `Bytes::new()` before awaiting or polling the next upstream chunk so `PooledSlice` permits are never retained across `.await` points (verified under 1-slab and 2-slab tight `BufferPool` tests). S3's mandatory part-checksum path only *try*-acquires its RAM budget while a body holds a pool slab and otherwise spools to disk instead of waiting.
   - **Pool-bounded vs. off-pool memory scope**:
     - `BufferPool` (`--max-buffer-mem`) bounds streaming disk/range-read slabs and 4 KiB-unit pooled slices.
     - **Off-pool allocations** remain bounded separately or scale with opt-in in-memory structures: HTTP client/response buffers (control-plane response bodies capped at `max_control_response_bytes = 16 MiB`), S3's separate `16 MiB` strict-hash RAM semaphore budget for `<= 4 MiB` uploads (larger strict-hashed uploads spill to disk), `LocalBackend`'s inline `<= 256 KiB` single-shot read/write buffers, `rship-crypto`'s per-stream OAE2 AEAD `64 KiB + 16 B` block buffers, SQLite page caches (`PRAGMA mmap_size = 0; temp_store = FILE;` with `cache_size = -4096` for `journal.db`, baseline/inventory shards, and raw ephemeral ingest DBs, and `-8192` for sorted `SqliteSyncIndex`), and intentionally in-memory collections (`MemorySyncIndex` `O(N)` entries when selected instead of disk-spilled `SqliteSyncIndex`, per-run conflict sets / bounded `RunReport` collections, and `--files-from` manifests).
   - **Verified isolated-subprocess Peak RSS gates**: `acceptance_gib_streaming_transfer_isolated_subprocess_peak_rss` streams 1 GiB across `16 × 64 MiB` concurrent files (`transfers = 8`, `part_concurrency = 4`, `8 MiB` `BufferPool`) inside an isolated subprocess and enforces `<= 64 MiB` true OS Peak RSS (~30 MiB observed; measured via Linux `VmHWM` with `getrusage` fallback, macOS `getrusage`, and Windows `GetProcessMemoryInfo`), alongside isolated-subprocess `<= 64 MiB` Peak RSS gates for 16 concurrent local transfers (`acceptance_16_concurrent_transfers_strict_buffer_cap_and_rss_under_64mib`) and 100k/1M-row `SqliteSyncIndex` runs (`acceptance_sqlite_sync_index_100k_rows_stays_under_64mib_rss`, `acceptance_sqlite_sync_index_1m_rows_rss_under_64mib`).
   - Work admission is strictly pull-driven (`mpsc::channel(256)` → fixed worker pool; `worker_threads = num_cpus.clamp(2, 8)`, `max_blocking_threads = 32` with 2 s idle reclaim, 3-frame local writer queue).
   - `rship-cli` enables `mimalloc` v3 (`no_thp`) by default (and unconditionally on `musl` targets) and installs low-RSS defaults (`arena_eager_commit=0`, `purge_decommits=1`, `purge_delay=10ms`, `arena_purge_mult=2`, `page_reclaim_on_free=1`, `allow_thp=0`) in OS pre-`main` constructors (`.init_array.00101` on ELF Unix, `__DATA,__mod_init_func` on Apple, `.CRT$XCU` on Windows) via `mi_option_set_default` (guarded by `mi_version() / 10_000 == 3`) so settings take effect before `std::rt::lang_start` allocates its first arena while preserving `MIMALLOC_*` env overrides (`--no-default-features --features all-backends` selects the system allocator); the `rship` SDK crate stays allocator-agnostic.

2. **Decoupled I/O Slices vs. Protocol Chunks**
   - *I/O Stream Slices* (`256 KiB` pooled) stream from `SeekableSource::read_at` / `read_into_slice` or `RemoteRangeReadable` into a single HTTP request body (0 extra API calls).
   - *Protocol Chunks* (`128 MiB` GDrive aligned to `256 KiB`; tiered `16–512 MiB` S3 respecting 10,000-part limit; `4 MiB` Dropbox; `320 KiB` OneDrive; `≤ 5 MiB` GDrive `multipart/related` & `≤ 16 MiB` S3 `PutObject` single-shot fast path) minimize QPS and PUT bills without buffering full multi-GiB protocol chunks in RAM.

3. **Write-Ahead Operation Journal & Ambiguous Commit Reconciliation**
   - Persist per-item intent (`op_id`, endpoint/account, source version, expected destination precondition, upload geometry, remote idempotency key) in SQLite **before** the first remote side effect:
     - `journal.db` runs **`WAL + FULL`** (`PRAGMA synchronous = FULL`, `wal_autocheckpoint = 2048`, `journal_size_limit = 16 MiB`, `foreign_keys = ON`) behind the group-commit `StateActor` with `ActiveOpIndex` fast-path lookup; lazily sharded `baselines/<pair_key>.db` (`WITHOUT ROWID`) and `inventory/<scope>.db` use `WAL + NORMAL`.
     - **Schema versioning & ordered migrations**: `journal.db`, baseline shards, and inventory shards stamp `PRAGMA user_version`, execute ordered migrations inside `BEGIN IMMEDIATE` transactions (treating unversioned pre-release DBs as version 1), and refuse to open databases whose `user_version` is newer than supported.
     - **Checkpointing, atomic batch rollback & safe shard deletion**: `StateActor` runs `PRAGMA wal_checkpoint(PASSIVE)` + `PRAGMA wal_checkpoint(TRUNCATE)` on **both** `Flush` and `Shutdown`; group-commit batches roll back atomically if `UPDATE jobs` counter preparation/execution or `COMMIT` fails, propagating the error to every touched batch write; deleting a SQLite shard closes its handle and unlinks `-wal` and `-shm` **before** the main `.db` file so orphaned WALs can never replay onto a recreated DB; early producer/observation/bisync errors finalize jobs as `Failed` and cleanly drain/join aborted workers.
   - **Pre-generated Google Drive IDs**: Google Drive pre-generates globally unique file/folder IDs via `files.generateIds` and persists `remote_op_id` in `journal.db` (via `StorageBackend::prepare_operation_id`) before single-shot uploads, `files.copy`, and folder creation (`mkdir`), enabling deterministic crash reconciliation (`files.get(id)`) with zero duplicates.
   - **Ambiguous commit reconciliation & source-version verification**: persist `Completing` intent before final commit; on ambiguous response (`404`/`NoSuchUpload`/crash), verify destination identity (`fileId` / `x-amz-meta-rship-op-id`) **and require `existing.src_version == current_src_ver`** before accepting reconciliation as completing the current transfer (a post-crash source edit triggers a fresh upload of the new version rather than falsely completing or deleting the edited source in `move`). Retries remain bound to a verified source version (`node_id/dev+ino, size, mtime_ns, ctime_ns` + racily-clean guard) and re-check before final commit to reject same-length middle edits / TOCTOU races.
   - **Safe advisory `ProcessLock` & scope limitation**: `sweep_stale_locks` unlinks stale `.lock` files **while holding the exclusive lock**, and `ProcessLock::try_acquire_file` verifies live file identity (`dev`+`ino` on Unix; `creation_time` + probe-lock contention on Windows) with bounded retry across concurrent unlink races, and briefly retries (~30 ms) while a sweeper holds a stale lock. **Unsupported**: `ProcessLock` hashes exact canonical scope keys and does not coordinate overlapping-prefix scopes (e.g. `a` vs. `a/b`); hierarchical lock scopes are planned for a future release.

4. **Namespace Identity, Pipelined Traversal & Three-Tree Bisync (Unison + Dropbox Canopy)**
   - Every observed `Entry` retains `(node_id, parent_id, raw_path, nfc_path)`.
   - Adaptive hybrid `SqliteSyncIndex` keeps small runs (`<= 32,768` entries) in RAM and transparently spills larger runs to a lazily materialized `LazyRunDir` with **isolated `src`/`dst` async writers** (`src_raw.db` / `dst_raw.db` → external-sorted `WITHOUT ROWID` `src_sorted`/`dst_sorted` in `sorted.db` using `journal_mode = OFF, synchronous = OFF, locking_mode = EXCLUSIVE, mmap_size = 0`, keeping blocking filesystem/lock I/O off async executor threads), detecting duplicate/NFC/case collisions explicitly without silent overwrites.
   - **Pipelined unordered transfers & streaming GDrive listing**: for non-ordered case-sensitive backends without duplicate names, `TransferEngine` pipelines source listings directly into transfer workers against a bounded destination snapshot (`<= 65,536` entries, transparently spilling to `SqliteSyncIndex` on larger trees); Google Drive streams `files.list` pages incrementally with bounded directory-tracker state (`AncestorNode` exact cycle checks + FIFO-bounded deduplication sets) and up to 8-way parallel shortcut resolution.
   - Persistent `sync_baseline` stores **dual-side** `(src_*, dst_*)` attributes, solving S3 `LastModified`/`ETag` false diffs and powering the **Three-Tree `bisync`** engine with zero-data-loss `keep-both` conflict resolution.
   - **Observation Completeness Gate, Empty-Side Guard & Version-Checked Mutations**:
     - Any error during source scan disables all destination deletions (`--delete-after` default + `--max-delete` circuit breaker), and missing local roots fail with `ErrorKind::NotFound` rather than returning an empty tree (including `--files-from` runs). A transfer worker that panics or stops accepting work is reported as a run error and marks source observation incomplete on every planning path (indexed, pipelined, streaming-merge), so no deletes run.
     - `bisync` persists `bisync_state` early (right after Phase 1 observation / before Phase 2 transfers) and checks existing pair baselines so even an interrupted first run arms the empty-side guard; `bisync` defaults to `--max-delete 50%` (`BisyncConfig::max_delete_percent = Some(50.0)`), while `sync` warns above 50% (`RunReport::high_delete_warning`) without aborting unless `--max-delete` is set.
     - Before Phase-3 deletes and Phase-2 overwrites (when the target lacks native conditional writes), `bisync` re-stats and verifies live entries match the observed `SourceVersion`, refusing to delete or overwrite concurrently modified files.

5. **OSDI-2014 Crash-Consistent Local Publication & Fast Copy**
   - OS-native local fast paths (`CopyFileExW` / `copy_file_range` / `fclonefileat` for large files; single-syscall `read_exact` + Windows in-handle `SetFileInformationByHandle(FileRenameInfo)` atomic staging for `<= 256 KiB` small files, with `verified_dirs` symlink-escape cache).
   - **Configurable local durability (`--fsync=always|batch|never`, default `batch`)**:
     - `always`: durable `sync_all()` + parent-dir fsync (Unix) / `MOVEFILE_WRITE_THROUGH` (Windows) on every write.
     - `batch` (default): defers per-file fsyncs during transfer. A `DurabilityFence` wraps the journal whenever a backend reports `StorageBackend::defers_durable_writes()`: baseline rows, operation retirements, and terminal job states (`Completed`/`Paused`, bisync state) are queued and committed only **after** `StorageBackend::flush_durable_writes` succeeds (`syncfs(2)` on Linux, falling back to parallel per-file/dir `fsync` only on `ENOSYS`/`EPERM`/`EOPNOTSUPP`; `FlushFileBuffers` on Windows; per-file/dir `fsync` on macOS/other Unix). The fence drains every 1,024 records or 2 s, before terminal job states, and on cancel/error paths. A failed flush poisons the fence, drops that batch's records, and fails the job; pending paths are kept rather than dropped. After a crash, a destination file with a leftover `Completing` operation is trusted only if a content hash shared by both sides matches, otherwise it is transferred again.
     - `never`: skips fsync on normal writes.
     - **Mandatory move/bisync durability**: before **any** source deletion (`move`, `bisync`), regardless of `--fsync` mode, the engine runs `StorageBackend::sync_durable_file` (durable `sync_all()`, parent-dir fsync, and fsync of newly created intermediate directories), then commits the record durably (`JournalStore::commit_verified_transfer_durable`), then re-verifies and deletes the source. `--backup-dir` copies are synced before the original is overwritten. Wrappers (`crypt:`) forward every durability hook to the inner backend.
     - Directory fsync errors propagate; only filesystems that cannot fsync directories (`EINVAL`/`ENOTSUP`/`ENOSYS`) are tolerated.
   - **Local preconditions & racily-clean guard**: `LocalBackend::{put_single_shot, server_side_copy, finish_upload}` verify `DstPrecondition` (`Absent` / `Existing { size, mtime_ns }`) immediately before atomic replacement; `LocalBackend::capabilities().mtime_granularity` is `10 ms` (`20 ms` on Windows, whose timestamps tick at ~15.6 ms) to protect against coarse kernel timestamp ticks. Writes over existing NFD-named destinations reuse the on-disk spelling.
   - `UploadTopology::ParallelParts` enables multi-stream cloud downloads and 4-core parallel OAE2 writes (`32 MiB` parts with CRC32C power-loss resume manifest).
   - Bijective `EncodingLayer` runs *before* Windows `\\?\` / `\\?\UNC\` verbatim conversion; Unix walkers skip FIFOs/sockets/devices via `symlink_metadata()`.

6. **Split-Plane Transport, Single Retry Layer & Streaming Checksums**
   - **Control Plane**: multiplexed HTTP/2 with `rustls-tls-native-roots` and optional `--ca-cert` / `--proxy` (HTTP, HTTPS, SOCKS5), with per-request `long_control_timeout` (`300 s` default vs. `60 s` standard `control_timeout`) for slow server-side operations: S3 `CopyObject` / `CompleteMultipartUpload`, GCS `rewriteTo`, Azure `PutBlockList` / `CopyBlob`, Dropbox `files/copy_v2` / `files/upload_session/finish`, GDrive `files.copy`, OneDrive `items.copy`, and WebDAV `COPY` / Nextcloud `.file` `MOVE`.
   - **Data Plane**: **`.http1_only()`** by default (avoiding TLS ALPN `h2` coalescing across concurrent bulk uploads and unbounded `h2` receive slabs) with transparent response decompression explicitly disabled (`.no_gzip().no_brotli().no_deflate().no_zstd()`) so wire bytes, `Content-Length`, `Content-Encoding`, range offsets, and checksums stay exact. Guarded by `ProgressWatchdog` byte-progress idle stall timeout (`30 s` default) plus post-body-EOF `data_finalize_timeout` (`300 s` default), using `SizedEofStream` to signal EOF at exact HTTP/1.1 `Content-Length` byte completion (including 0-byte uploads). Data-plane response bodies are read through `HttpTransport::read_data_body` with both an idle (`data_stall_timeout`) and a total (`data_finalize_timeout`) bound. **Known limit**: EOF is signalled when the final bytes are handed to hyper, not when they leave the socket, so a network blackhole during the buffered upload tail is caught by the `300 s` finalize timeout rather than the `30 s` stall timeout.
   - **Single Retry Layer, Adaptive Control & Non-Idempotent Reconciliation**:
     - All 7 HTTP cloud providers route through `rship_backends::common::http::execute_with_policy*` with `Error::retries_exhausted` preventing outer engine retry stacking, full-jitter exponential backoff (seedable for simulation replay), a single `30 s` backoff / `Retry-After` cap (`DEFAULT_MAX_RETRY_DELAY`), and `set_sensitive(true)` on bearer/auth headers. Engine and backend retries draw from **one** retry bucket per destination `(remote, principal)` (`StorageBackend::retry_quota()`, AWS token-bucket defaults `500 / 5 / 10 / 1`), shared across a whole `sync` or `bisync` run. A `429` is resent without reconciliation (RFC 6585: not processed).
     - Per-`(remote, principal, LimiterPlane)` isolation separates Control Plane and Data Plane limiters (`--tpslimit`, single-cut-per-window `0.5 s` CUBIC coalescing concurrent throttles, and write-QPS buckets); Falcon dual-lane adaptive concurrency (`--adaptive`) uses windowed live-byte accounting and non-blocking `FalconRouter` per-lane dispatch.
     - Ambiguous failures on non-idempotent mutations reconcile server state instead of blindly retrying, and reconcile must *prove* the result is ours: S3 `CopyObject` `412` / `CompleteMultipartUpload` via `x-amz-meta-rship-op-id`; Azure `PutBlockList` / `CopyBlob` and GCS `rewriteTo` via op-id metadata plus size; Google Drive via pre-generated `files.generateIds`; Dropbox `copy_v2` (size + `content_hash`), `move_v2` (pre-recorded file id) and `upload_session/finish` (new revision with our size and `client_modified`); OneDrive `items.copy` / `createFolder`; WebDAV `MOVE`/`MKCOL`/`DELETE` via `PROPFIND`, and `COPY` only if the destination changed from a pre-COPY snapshot and matches the source size. Upload reconcile on backends that cannot tag objects with the op id (OneDrive, Dropbox, WebDAV, SFTP, local) follows the shared `common::reconcile` rules: source size, the mtime we set where the provider keeps it, and a version identity (OneDrive eTag snapshotted at session start, Dropbox `rev`, WebDAV ETag, local `dev`+`ino`) that changed from the pre-op object. An object that cannot be attributed to the operation is `NotCommitted`, so the engine re-transfers rather than trusting a same-size older file.
     - Shared `rship_transport::oauth` PKCE + single-flight refresh engine serializes refreshes across processes via `FileTokenStore::lock_refresh` (offloaded off async threads) with TTL-clamped proactive refresh margins.
   - **Zero-Spool Streaming Checksums & End-to-End Verification**: `StreamingHashStream` and `VerifyingDownloadStream` compute and verify digests on the fly without disk spooling, paired with engine post-commit `verify_committed_checksum` before retiring operations, recording baselines, or deleting moved sources. Chunked uploads are verified against the source's full-object checksum when one exists: sequential sessions keep a running SHA-256/CRC-32C and hold back the final bytes until it matches; parallel multipart combines per-part CRC-32C (`crc32c_combine`) before `finish_upload`.
   - **Integrity failures are never reconciled into success**: checksum mismatches are `ErrorKind::Integrity` / `RetryClass::Integrity`, never a throttle signal, and never accepted through reconcile. The transfer is retried from scratch (at most twice); a corrupt object we created is deleted, and one that cannot be removed (or that overwrote a pre-existing version) gets a persisted `integrity_failed` journal marker that forces re-transfer and blocks skips, baselines, bisync convergence, and `move` source deletes until a verified transfer clears it.
   - **Per-provider verification matrix** ("unverified" means length-checked only on the wire; independently, the engine checks chunked *source reads* against the source's full-object checksum as described above):

     | Provider | Upload single-shot | Upload chunked | Download full | Download ranged |
     | :--- | :--- | :--- | :--- | :--- |
     | S3 | `CRC64NVME`/`CRC32C` header (server-checked), MD5 ETag | per-part checksum header; COMPOSITE parts required in Complete | ETag MD5 / `x-amz-checksum-*` | unverified |
     | GCS | streamed CRC32C vs response; source CRC32C/MD5 checked by GCS | running CRC32C sent as `x-goog-hash` on the final request (server-checked); unverified after cross-process resume | `x-goog-hash` CRC32C, else MD5 | unverified |
     | Azure Blob | Content-MD5 | whole-blob MD5 when blocks upload in order (sent as `x-ms-blob-content-md5`); otherwise unverified | Content-MD5 | unverified |
     | Google Drive | streamed MD5 vs response | unverified | `md5Checksum` | unverified |
     | Dropbox | streamed `content_hash` vs response | unverified | `content_hash` | unverified |
     | OneDrive | QuickXorHash (+ SHA-256 when returned) | running QuickXorHash, final chunk; unverified after cross-process resume | SHA-256, else QuickXorHash | unverified |
     | WebDAV (Nextcloud) | `X-Hash-MD5`; source MD5 stored as `OC-Checksum` | `X-Hash-MD5` per chunk | `OC-Checksum` MD5 if stored | unverified |
     | WebDAV (ownCloud) | server-checked `OC-Checksum` MD5 when source MD5 known | assembled file via `OC-Checksum` when source MD5 known | `OC-Checksum` MD5 if present | unverified |
     | WebDAV (other), SFTP, local | unverified (local relies on fsync + CRC32C part manifest) | unverified | unverified | unverified |

7. **Zero-Knowledge STREAM OAE2 Encryption (`rship-crypto`)**
   - `#![forbid(unsafe_code)]` hardware-accelerated (`aws-lc-rs` AVX2/NEON + once-per-file `HChaCha20` subkey derivation) seekable 64 KiB `XChaCha20-Poly1305` in-place AEAD blocks with strict header reserved-flag validation and zeroized buffers on auth failure or drop.
   - Argon2id + HKDF-SHA256 key derivation with `zeroize` key material hygiene and deterministic canonical base32 SIV filename encryption over any backend.

8. **Unified Lazy SDK Runtime (`rship`) & Modular Provider Registry**
   - `crates/rship` owns the `#[non_exhaustive]` declarative `AppConfig` / `*RemoteConfig` fluent builders (with `RemoteConfig::visit_secrets*` as single source of truth for secret redaction & keyring lifecycle), OS Keyring resolution, `rclone.conf` import, `factory::resolve_backend`, and the **lazy** `RshipClient` runtime.
   - `RshipClient` initializes `HttpTransport` only for HTTP cloud remotes (pure local and SFTP paths skip TLS root-cert loading & HTTP pools) and opens `StateActor` (`journal.db`) only on durable journal/inventory operations.
   - `rship-cli`'s `CliRuntime` delegates directly to `RshipClient` so the CLI and embedded Rust apps share one backend cache, resolution pipeline, and lifecycle; `rship-cli` adds only terminal ergonomics (`ui.rs`, live `--tui`), typed exit-code errors (`errors.rs`), and the `providers/{mod,bundle,oauth,filters}.rs` `ProviderAdapter` auth/export/GC registry.
   - Core crates enforce `#![forbid(unsafe_code)]` across 5 of 7 crates (`rship-core`, `rship-state`, `rship-transport`, `rship-crypto`, `rship`) and workspace-level `clippy::undocumented_unsafe_blocks`.
