Measured head-to-head with MD5 bit-exact verification across two environments using the default **`rship 0.1.0`** release build (tuned `mimalloc` v3 with `no_thp` and bounded `2..=8` Tokio workers — **every workload strictly under 64 MiB RSS**):

- **1 Gbps Linux VPS (Live Google Drive)**: Debian 13 · 4 vCPU AMD EPYC · RAM-backed `tmpfs` (zero disk bottleneck) · exact Linux kernel `wait4` `ru_maxrss` — **`rship 0.1.0`** vs **`rclone v1.60.1-DEV`** hitting the same Google Drive account.
- **Local Windows 11 NVMe**: alternating-order rounds · Win32 `PeakWorkingSetSize` — **`rship 0.1.0`** vs **`rclone v1.76.0`**.

<Callout type="info" title="How rship Keeps mimalloc Strictly Under 64 MiB RSS">
`rship-cli` enables `mimalloc` v3 with `no_thp` (64 KiB Linux purge granularity instead of 2 MiB THP), configures low-RSS defaults at startup (`arena_eager_commit=0`, `purge_decommits=1`, `purge_delay=10ms`, `arena_purge_mult=2`, `page_reclaim_on_free=1` — all overridable via `MIMALLOC_*` env vars), bounds Tokio async workers to `2..=8` with fast blocking-thread reclaim, and caps off-pool local writer queues to 3 frames. You can also build with `--no-default-features --features all-backends` to use the platform system allocator.
</Callout>

## Reproduce Locally

```bash
# Standard quantitative suite (16-concurrency RSS <= 64 MiB, 100k-row SQLite RSS, 10 GiB GDrive plan)
cargo test --release -p rship-cli --test acceptance_benchmarks -- --nocapture

# Full 1,000,000-row (500k src + 500k dst) SQLite SyncIndex RSS verification (default tuned mimalloc)
cargo test --release -p rship-cli --test acceptance_benchmarks \
  acceptance_sqlite_sync_index_1m_rows_rss_under_64mib -- --ignored --nocapture

# Compare against the platform system allocator
cargo test --release -p rship-cli --no-default-features --features all-backends \
  --test acceptance_benchmarks \
  acceptance_sqlite_sync_index_1m_rows_rss_under_64mib -- --ignored --nocapture
```
